# DATABASE_DESIGN.md

**Design Baseline Version:** 1.1
**Status:** OWNER APPROVED — FROZEN FOR V1 IMPLEMENTATION (approved 2026-10-20)
**Source:** Step 7 as approved, plus every later schema correction, **synchronized with the completed Owner Review and the final Owner business changes** (OWNER_REVIEW_NOTES.md, OPEN_QUESTIONS.md §2): manual appointment duration with overlap allowed, arrival events, follow-up statuses, Doctor / Sales / Manager discount entries before Visit finalization, Patient Credit ledger, Lab-First fixed-lab distribution, Walk-In / Direct patients with zero Sales commission (no shared pool), monthly payroll, Assistant and Sales attendance, Assistant overtime, Assistant base pay + overtime payroll, Sales-recordable Materials / Petty expenses, editable audited expenses, dual-entry feedback (website token and Sales-entered) with no expiry, Manager-set passwords. **Final correction pass:** every foreign key audited for PostgreSQL implementability (§24), Doctor-only initial price / Fixed Lab / Ortho terms, Manager-only revisions, Sales commission rate history (future collections only), Sales-entered feedback linked to its request, expense creator preserved. Obsolete structures (attribution holds, pending attributions, same-slot uniqueness, expense finalization, feedback expiry, reset flags, Walk-In pools, Doctor-only discount, `final_amount = salary_snapshot`) are not reproduced.

Labels: **CONFIRMED** = a business rule the Owner stated. **TECHNICAL** = engineering choice with no business meaning. **DEFAULT** = a technical default that can be vetoed. **OPEN / DEFERRED** = intentionally not decided in the design (only OPS-1 key locations and Q-ORT-3b, the Ortho total-price decrease, DEFERRED / OPEN FOR FUTURE VERSION: V1 rejects it with `ortho.total_decrease_not_supported`); nothing is implemented for them beyond that rejection.

There is no Inventory table, no X-ray table and no imaging column anywhere in this schema. "Medical Supplies" exists only as an expense-category row.

## 1. Conventions

| Item | Convention |
|---|---|
| Keys | `uuid` primary keys (time-ordered). Human-readable codes only where confirmed (`patient_code`). |
| Money | `numeric(12,2)`, EGP. Percentages are `numeric(5,2)` with `CHECK 0..100`. Application arithmetic uses `decimal`, never floating point. |
| Time | `timestamptz` (UTC) for moments. `date` for calendar dates (due dates, payroll periods), interpreted in the clinic-local timezone. |
| Every table | `created_at`, plus `created_by_user_id` where a person acts. |
| Concurrency | **RV** = PostgreSQL `xmin` row-version token (API: ETag / `If-Match`). |
| Deletes | No physical deletes in business schemas. All FKs are `ON DELETE NO ACTION`; no cross-schema cascades. Soft markers (`voided_at`, `removed_at`, `withdrawn_at`, `is_active`) where needed. |
| **H** | Historical, insert-only. `clinic_app` has no UPDATE or DELETE grant. |
| **L** | Lifecycle. Only the named columns may change. Everything else is frozen. |
| **M** | Mutable current state. Updates allowed; every change is audited with old and new values. |
| **A** / **A+** | **A** = automatic audit through the SaveChanges interceptor. **A+** = additionally an explicit semantic audit event. |

## 2. Cross-module references, schemas and migrations

- **Cross-module EF navigation: avoid.** Module entities are `internal`; cross-module references are scalar id properties.
- **Database foreign key constraint: keep.** Every reference to a business entity is a real PostgreSQL FK. All cross-schema FKs are declared in one reviewable file, `CrossModuleReferences.cs`, in the persistence host project, using one-sided `HasOne<Other>().WithMany().HasForeignKey(...)` with no navigation properties. An architecture test compares that file to the database.
- **FK direction is free.** Only code dependencies follow the module levels. `finance.patient_charges → clinical.treatment_cases` is a valid FK even though Finance never calls Clinical code.
- **No duplicate entities.** A business entity lives in exactly one table. The only deliberate copies are listed in section 20.
- **Polymorphic references (no FK, intentional; each is paired with a discriminator column and verified by a command check):** `audit.audit_log.entity_id`, `notifications.related_entity_id`, `clinical.visit_corrections.record_id` (with `record_type`), `crm.responsibility_history.entity_id` (with `entity_type`). Nothing else is polymorphic.
- **Foreign-key implementability rule (final correction pass).** A foreign key is documented only if PostgreSQL can create it: every composite FK targets a `PRIMARY KEY` or a declared `UNIQUE` constraint on **exactly** the referenced column set, with identical column types; every simple FK targets a primary key. The complete register of composite FKs and their parent UNIQUE targets is §24. Nullable composite FKs use `MATCH SIMPLE` (a NULL in any FK column skips the check), so every nullable composite FK is paired with a CHECK that makes the NULL pattern explicit.
- **Schema = module.** Business schemas: `identity`, `audit`, `configuration`, `staff`, `patients`, `scheduling`, `clinical`, `prescriptions`, `orthodontics`, `crm`, `finance`, `expenses`, `payroll`, `notifications`, `feedback`. Infrastructure schemas: `infra` (migration history, Data Protection keys, guard functions) and `hangfire`.
- **Migrations.** One DbContext, one history table in `infra`. Each migration is named `<date>_<Module>_<Change>`; a migration touches one module's schema, except cross-module FK additions named `<date>_Xref_<Change>`. A test fails if any table's schema differs from its owning module.
- **Database roles.** `clinic_migrator` (DDL, run by CI/migrator only), `clinic_app` (DML only: no DDL, no DELETE on business schemas, no UPDATE on **H** tables), `clinic_worker` (least privilege, section 10), `clinic_backup` (explicit SELECTs, section 10).

**Patient Medical History database tests (v1.1):** (1) a second row for the same patient is rejected; (2) a row without an existing patient is rejected; (3) inserting a row with all flags omitted stores NULL, never FALSE, in every flag column; (4) updating a flag to NULL is accepted and a read returns NULL; (5) `last_dental_visit` accepts "6 months ago", "last year" and "I don't remember" and rejects a value over 200 characters; (6) `clinic_app` cannot DELETE the row; (7) `clinic_worker` cannot SELECT it; (8) `clinic_backup` can SELECT it and write nothing; (9) `patients.patients` has no `medical_history`, `chronic_diseases` or `previous_surgeries` column.

**Age display (DTO rule):** DOB present → current age computed from DOB. Only a recorded age → "Age recorded at registration: N (recorded on D)"; never aged forward. Same for Doctor DTO, Sales DTO, Manager view and prescription print model.

**Released availability (Q-APP-1).** The *booked range* of an appointment is `[start_at, start_at + duration]`. Its **effective booked end** is `LEAST(start_at + duration, visit_ended_at)` when `visit_ended_at` is set, otherwise the nominal end. The Appointment is never deleted or altered: the unused future part simply stops counting as booked, computed in the view `scheduling.v_effective_booked_ranges` (owned by `clinic_migrator`, read by scheduling queries). Overlaps are allowed, so the view is informational (the calendar shows concurrent bookings); it also never *extends* a range past its nominal end.

**Doctor arrival queue.** Derived, never stored: appointments of the signed-in Doctor where a live arrival exists for today (clinic-local), `status IN ('Scheduled','Confirmed')`, and no Visit started for the appointment (`visits.appointment_id` absent). Ordered by `arrived_at`. Starting the linked Visit sets the Appointment to **InTreatment**, which removes it from the queue. The queue DTO carries patient name, age display, reason, appointment time and arrived time — no contact data.

`reason` is Doctor-visible; `sales_notes` is Sales/Manager only. `kind` is a discriminator so the reminder job can emit "Implant Follow-Up Tomorrow".

## 11. orthodontics

**Ortho price vocabulary (one meaning each, used package-wide).** **Gross Ortho Total** = `gross_total_price`, the Total Price the Doctor enters in the terms, later increased only by the Manager through `Orthodontics.Terms.Edit`. **Discount** = the fixed-EGP pre-finalization discount snapshot (`patient_charges.discount_amount`), set by the Doctor, Sales or Manager on the ortho pricing line before the Visit is finalized; it never changes afterwards and is never re-applied to an increase. **Effective Ortho Total** = Gross Ortho Total − Discount = the **Ortho Charge Billed** (`final_price` + Σ `OrthoTermsChange` adjustments); it is what the patient actually owes. The bare word "Total" is not used for the ortho schedule. At charge establishment: `original_price` = Gross, `discount_amount` = Discount, `final_price` = Effective.

**Flow (single, authoritative).** (1) During the editable Visit the Doctor creates the case and `SetInitial` **stores** revision 1 (Gross Total, Deposit, Months); the work item's `entered_price` = Gross; **no charge and no installment exists**. (2) Doctor, Sales or Manager may set the fixed-EGP Discount on the line. (3) The Doctor finalizes the Visit: Clinical calls Finance, which snapshots the Discount and establishes the Charge (Effective = Gross − Discount); Finance publishes `ChargeEstablished` (in-process, same transaction) and the Orthodontics handler validates **0 ≤ Deposit ≤ Effective** (otherwise the whole finalize fails with 422 `ortho.deposit_exceeds_effective_total` and nothing is written; the Deposit is never silently altered), sets `ortho_cases.charge_id` and generates the initial schedule **once**. (4) Initial schedule = `Months` equal `Generated` installments from `Effective − Deposit`, the last absorbing the rounding; first due date one month after the charge date. Worked example: Gross 20,000, Discount 2,000, Deposit 5,000, Months 5 → Effective 18,000; base 18,000 − 5,000 = 13,000 → 5 × 2,600; 5,000 + 13,000 = 18,000; Charge original 20,000, discount 2,000, billed 18,000; no extra 2,000 outstanding.

**Derived (never stored):**
- Per installment: current revision = latest; **active** = latest `is_active`; current amount, current due date; **`amount_already_paid` = Σ `installment_payments.amount_applied`**; remaining = amount − amount already paid; status (Upcoming / Due / Partially Paid / Paid / Overdue) from clinic-local date, current due date and applied amounts (remaining 0 ⇒ Paid); a retired installment is shown in history only and is not payable.
- Per case: Effective Ortho Total (= Charge Billed = current Gross − Discount); Remaining price = Effective − current Deposit; Deposit paid = `min(deposit, Σ ortho allocations − Σ applications)`.
- **Schedule validity.** `active_schedule_amount` = Σ current amount of **active** installments. **`schedule_difference` = Effective Ortho Total − current Deposit − `active_schedule_amount`.** `active_regular_count` = number of **active** installments with origin `Generated` or `ManagerAdded` (`PriceChange` difference installments are excluded: they never stand in for the regular plan). **`month_plan_difference` = current `number_of_months` − `active_regular_count`.** **`requires_schedule_adjustment` = (`schedule_difference` ≠ 0) OR (`month_plan_difference` ≠ 0).** **`schedule_is_balanced` = (`schedule_difference` = 0)**; **`month_plan_conforms` = (`month_plan_difference` = 0)**. These are derived read-model fields, **not** a lifecycle status and not stored columns. A schedule with `requires_schedule_adjustment = true` is **never treated as valid or finalized**: the case shows a warning and both differences until the Manager corrects it.

**Command-level invariants (tested):**
1. **Always:** Gross ≥ 0; 0 ≤ Discount ≤ Gross; Deposit ≥ 0; **Deposit ≤ Effective Ortho Total**; every installment amount ≥ 0; every installment amount ≥ its `amount_already_paid`; a retired installment has no payment history; `number_of_months` ≥ 1.
2. **A valid schedule satisfies both:** **Deposit + Σ active current installment amounts = Current Effective Ortho Total** (not the undiscounted Gross) **and** `active_regular_count` = `number_of_months`. Payments change only Paid, Remaining and status; they never change a schedule amount, so they cannot unbalance it.
3. **Initial creation = Visit finalization (never earlier).** `SetInitial` stores revision 1 only. At finalization the Discount is snapshotted, Effective = Gross − Discount, the Deposit is validated (`0 ≤ Deposit ≤ Effective`, else `ortho.deposit_exceeds_effective_total`: e.g. Gross 20,000, Discount 18,000, Deposit 5,000 → Effective 2,000 < 5,000 → the finalize fails, nothing is written), the Charge is established and `Months` equal installments are generated **once** from `Effective − Deposit`, the last absorbing the rounding (G10). No installment exists before finalization.
4. **Gross Total increase of Δ (Manager `Terms.Edit`):** Gross 20,000 → 24,000 with an established Discount of 2,000 (Effective 18,000 → 22,000, Δ = 4,000) inserts an `ortho_term_revisions` row, a `finance.charge_adjustments` row (`OrthoTermsChange`, +Δ) and exactly one `PriceChange` installment of Δ (due one month after the latest due date among active installments, or one month after the charge date if none); the **Discount snapshot stays 2,000 and is not re-applied to Δ**; existing installments, applications and allocations are untouched; nothing is redistributed. The equation `Deposit + Σ active = Effective` therefore holds again (5,000 + 13,000 + 4,000 = 22,000) if it held before; `month_plan_difference` is unchanged (a `PriceChange` row is not regular).
5. **Gross Total decrease:** **not supported in V1.** Rejected with `ortho.total_decrease_not_supported` before any write; no negative installment, no automatic reduction, no `DiscountCorrection` / `PriceCorrection` workaround, no silent rewrite (Q-ORT-3b is DEFERRED / OPEN FOR FUTURE VERSION).
6. **Deposit change after installments exist (Manager `Terms.Edit`):** validated `0 ≤ Deposit ≤ Effective`; only the revision row is inserted; **no regeneration and no redistribution**. Example (no discount): Effective 20,000, Deposit 5,000 → 7,000 → required Σ = 13,000; if it was 15,000, `schedule_difference` = −2,000 until the Manager's batch brings Σ to 13,000. With the 2,000 Discount: Effective 18,000, Deposit 5,000 → 7,000 → required Σ = 11,000.
7. **Months change after installments exist (Manager `Terms.Edit`):** `number_of_months` ≥ 1 and **≥ the number of active regular installments that have payment history** (those can never be retired); otherwise rejected with `ortho.months_conflict_with_paid_history` and nothing is written. Otherwise only the revision row is inserted: **no installment is generated, added, removed or redistributed automatically.** `month_plan_difference` becomes ≠ 0 (e.g. 10 → 12 gives +2: two regular installments are missing; 10 → 8 gives −2: two are surplus), so `requires_schedule_adjustment = true` until the Manager manually adds or retires regular installments (and rebalances amounts) in the schedule batch. `number_of_months` is therefore never dead metadata: it defines the month-plan rule.
8. **Manager schedule batch (`Installments.Edit`), atomic.** Operations: **revise the amount** of an active installment (≥ `amount_already_paid`); **revise the due date** of an **unpaid** installment (no applications; the previous due date stays in the revision history); **add** a future installment (`ManagerAdded`, due date ≥ clinic-local today, amount ≥ 0, no payment history, next `installment_number`); **retire** an **unpaid** active installment (no payment history at all; `ManagerRetire`, never a delete). Every operation needs the batch reason and writes a revision. At the end of a successful batch all of these hold, otherwise **nothing is written**: (a) no active amount negative; (b) every installment amount ≥ its `amount_already_paid` (`ortho.installment_below_paid_amount`); (c) no installment with payment history retired or re-dated (`ortho.installment_has_payment_history`); (d) `active_regular_count` = `number_of_months` (`ortho.month_plan_mismatch`); (e) **Deposit + Σ active current amounts = Effective Ortho Total** (`ortho.schedule_unbalanced`).
9. **Immutable payment history:** `installment_payments` rows and `payment_allocations` are never changed by any terms or schedule edit; an installment with application history is never deleted (no DELETE grant), never retired, never reduced below what was applied, and its payments never move.
10. **Generic correction guard (G9):** a charge that is an ortho charge accepts **no** `DiscountCorrection` and **no** `PriceCorrection`; its only adjustment kind is `OrthoTermsChange`, written only by the terms-edit command. All Ortho Total changes go through `Orthodontics.Terms.Edit`. Payment reversal, refund and correction on the Ortho charge are unaffected.

## 15. payroll

Payroll is **monthly** (Q-PAY-2) for Doctor, Sales and Assistant. A payroll period is a **calendar month**: `period_start` = first day, `period_end` = last day of the same month in clinic-local time (`CHECK period_start = date_trunc('month', period_start)::date AND period_end = (period_start + interval '1 month - 1 day')::date`). **Appointment status database tests:** (1) status `Arrived` or `Waiting` is rejected by the CHECK; (2) the seven allowed values are accepted; (3) `scheduling.appointments` has no `arrived_at` or `checked_in_by_user_id` column; (4) two Scheduled appointments for the same Doctor and the same `start_at` are both accepted (overlap allowed); (5) `duration_minutes` NULL or 0 is rejected; (6) `appointment_arrivals` does not change `appointments.status`; (7) a second live arrival for one appointment is rejected, a voided one allows a new arrival.

## 18. Data-integrity rules and guards

| Rule | Mechanism |
|---|---|
| **R1** Ledger and history tables are insert-only | `patient_charges`, `charge_adjustments`, `payments`, `payment_allocations`, `patient_credit_entries`, `payment_corrections`, `distribution_events`, `doctor_entitlements`, `doctor_earnings`, `revenue_distributions`, `fixed_lab_expenses`, `fixed_lab_revisions`, `lab_percentage_history`, `ortho_term_revisions`, `sales_commission_rate_history`, `ortho_installments`, `ortho_installment_revisions`, `installment_payments`, `appointment_arrivals` (except void columns), `visit_corrections`, `pricing_discount_entries`, `feedback_entries`, `responsibility_history`, `follow_up_contact_attempts`, payroll item / adjustment tables (including overtime items), `root_canal_measurements` (after finalization), `audit_log`: `clinic_app` has no UPDATE / DELETE grant. |
| **R2** Visit-owned clinical records are editable until the visit is finalized, and afterwards only by the controlled correction path | G1 |
| **R3** Payroll snapshot columns frozen; status transitions allowed | G2 |
| **R4** No business-schema DELETE | `clinic_app` has no DELETE grant |

- **G1 – finalized-visit guard (Q-CLN-1).** One shared trigger function in `infra`, attached to `treatment_records`, `treatment_steps`, `root_canal_measurements`, `prescriptions`, `prescription_items` and visit notes. On UPDATE (or INSERT of a new measurement) it checks whether the owning visit is Finalized. If so the change is rejected **unless** (a) the transaction carries `SET LOCAL clinic.audited_correction = 'on'` **and** (b) a `clinical.visit_corrections` row exists for this transaction (`txid = txid_current()`) whose `correcting_doctor_id` equals the visit's own doctor. Only the Doctor-correction code path satisfies both; it writes the audit entry in the same transaction. The Visit is never reopened, no Manager approval is needed, the Manager has no clinical-correction right, and price / discount / consultation fee are outside this path.
- **G2 – payroll sealing.** Applies to `doctor_payrolls`, `sales_payrolls` and `assistant_payrolls` (sealed money and source / reason columns) and their item / adjustment tables, including `assistant_payroll_overtime_items` and `sales_payroll_commission_items` (whose insert trigger also verifies employee, month, deactivation date and the effective rate revision; a rate change never alters an existing item). Rejects any change to sealed columns, or insertion of items / adjustments, once `finalized_at IS NOT NULL`; verifies at finalization that `assistant_payrolls.overtime_amount = Σ items` and `final_amount = base_pay_amount + overtime_amount`; rejects an overtime item whose entry belongs to another Assistant, lies outside the payroll month or is voided; rejects voiding an overtime entry that a payroll item references; rejects setting `finalized_at` before the end of the payroll month (clinic-local); rejects a Doctor payroll item whose earning's doctor or month differs from the payroll. `status`, `finalized_at`, `paid_at` stay updatable. Because every `doctor_earnings.recognized_at` is the server time of the collection, no earning can appear in an already-finalized month.
- **~~G3~~ – retired.** Expenses have no sealing (Q-EXP-2). The identifier is not reused.
- **G4 – charge/payment consistency.** Declarative only: generated `final_price`, composite FKs keeping patient consistent, sign CHECKs on payments, allocations and credit entries, `reverses_*` CHECKs. No triggers.
- **G5 – allocation cap** on `installment_payments` (insert trigger): locks the allocation row `FOR UPDATE`; Σ `amount_applied` for the allocation including the new row must not exceed the allocation amount; sign must match; the installment's applied total must not exceed its current amount. **(b) Reverse direction:** an insert trigger on `ortho_installment_revisions` locks the `ortho_installments` row `FOR UPDATE` and rejects a revision whose `amount_due` is below the installment's net applied amount (`amount_already_paid`); both directions take the same lock, so a concurrent application and edit serialize. **(c) Retirement and activity:** a revision with `is_active = false` is rejected if the installment has **any** `installment_payments` row; a revision after a retirement may not set `is_active = true`; an application insert is rejected when the installment's current revision is inactive. **(d) Due date:** a revision that changes `due_date` is rejected if the installment has any `installment_payments` row; a new `ManagerAdded` revision 1 must have `due_date` ≥ the clinic-local current date (checked by the command, repeated by the trigger with the transaction timestamp).
- **G6 – work-item and pricing freeze.** Rejects changes to frozen columns, to `entered_price` once a charge references the item, and any insert into `pricing_discount_entries` once the line's Visit (resolved through the work item's treatment record, or `consultation_visit_id`) is Finalized or a charge exists for the line; verifies `amount ≤ price` for the line at finalization.
- **G7 – fixed-lab eligibility and initial-entry precondition.** (a) Insert trigger on `fixed_lab_expenses` requires `procedure_types.lab_model = 'Fixed'`. (b) **Deferred constraint trigger on `patient_charges`**: a Treatment charge whose `lab_model = 'Fixed'` requires, at commit, a `fixed_lab_revisions` row with `revision_number = 1` for its case. An unknown Fixed Lab is therefore never distributed and never treated as 0; the Visit-finalize command reports `fixed_lab.initial_required` before reaching the database. (c) `fixed_lab_revisions` role/number CHECK (Doctor = revision 1, Manager = later).
- **G8 – payment conservation (deferred constraint trigger, at commit).** For every payment touched in the transaction: `payments.amount = Σ payment_allocations.amount + Σ patient_credit_entries.amount` (credit entries of that payment). A patient's credit balance must be ≥ 0 and no allocation may push a charge's net allocated amount above its Billed or below 0.
- **G9 – ortho-total guard (generic adjustments cannot change an Orthodontic Total).** (a) Insert trigger on `charge_adjustments`: if the charge is an ortho charge (`EXISTS ortho_cases WHERE charge_id = NEW.charge_id`) the row must have `adjustment_kind = 'OrthoTermsChange'` and `amount_delta > 0`; `OrthoTermsChange` is rejected for any charge that is not an ortho charge; `DiscountCorrection` / `PriceCorrection` are rejected for ortho charges. (b) Insert trigger on `ortho_term_revisions`: `gross_total_price` may not be lower than the previous revision's (V1: no decrease; the one place to relax when Q-ORT-3b is answered). (c) Deferred constraint trigger: for an ortho charge, `original_price` = revision-1 `gross_total_price` and `Σ OrthoTermsChange.amount_delta` = current `gross_total_price` − revision-1 `gross_total_price`, so the charge's Billed (= Effective Ortho Total) and the term revisions cannot drift apart. (d) Deferred constraint trigger: for an ortho case with a charge, the current revision's `deposit_amount` ≤ the charge's Billed (`final_price` + Σ `OrthoTermsChange`). The command layer reports the friendly errors (`ortho.use_terms_edit`, `ortho.total_decrease_not_supported`) before the database is reached; the guard is the backstop. No table is added.
- **G10 – initial-schedule guard (Orthodontics).** (a) An insert of a `Generated` installment is rejected unless the case's `charge_id` is already set (no schedule before Visit finalization) and the case has no `Generated` installment yet (generated **once**). (b) Deferred constraint trigger: every ortho case with a `charge_id` has exactly `number_of_months` (revision 1) `Generated` installments whose revision-1 amounts sum to the charge's `final_price` − revision-1 `deposit_amount`, with revision-1 `entered_by_role = 'DOCTOR'`. So an ortho Charge without its initial schedule, or a second generation, cannot commit. The friendly errors come from the finalize handler first.
- **G8b – distribution identity (deferred constraint trigger, at commit).** For every `distribution_events` row: `Σ(lab_amount + clinic_share) + Σ doctor_earnings.amount = basis_amount`; for every allocation `0 ≤ Σ doctor_earnings ≤ Σ doctor_entitlements`; no cumulative per-allocation `clinic_share` is negative.

Not enforced by the database (command-handler checks plus integration tests): the actor of a `pricing_discount_entries` / `entered_price` write is the Visit's Doctor (price) or an allowed role (discount); ortho cases accept exactly one work item and one charge; the Sales deactivation redistribution (including the no-Active-Sales unassigned path); the record's visit is not cancelled; the snapshot copies match (work item → charge); arrival eligibility; the Sales-recordable expense category rule's role check;  the schedule balance and the month plan (`schedule_difference`, `month_plan_difference`) are derived flags, enforced as command rules only at the Manager schedule batch (a terms edit may legitimately leave the schedule temporarily needing adjustment); the Deposit-versus-Effective validation at finalization is checked by the finalize handler and backed by G9(d).

## 24. Foreign-key implementability register (PostgreSQL)

This register is the result of the full audit. PostgreSQL accepts a foreign key only if the referenced columns carry a `PRIMARY KEY` or `UNIQUE` constraint on **exactly that column set** (any column order), with identical types. Every composite FK in the schema is listed with the constraint that backs it. EF Core generates the parent constraints as `HasAlternateKey(...)` (unique constraint) and the FKs with `HasForeignKey(...).HasPrincipalKey(...)`.

**General rules verified for every table.** (a) All primary keys are `uuid`, except `audit.audit_log.id` (bigint), `identity.permissions.key` (text), `configuration.payment_methods.code` (text) and `configuration.settings.key` (text); every FK column has the type of its target. (b) Every simple FK targets the parent's primary key. (c) All FKs are `ON DELETE NO ACTION` (no cascades, no SET NULL). (d) No FK targets a view. (e) Nullable composite FKs use `MATCH SIMPLE` and each is paired with a CHECK defining the NULL pattern (listed below). (f) No FK cycle requires deferred insertion: insertion order is Identity → Staff → Patients → Scheduling → Clinical (visit → cases → records → work items) → Feedback request → Finance (charges → payments → allocations → events → entitlements / earnings / distributions) → Ortho → Payroll. (g) Self-FKs: `identity.users.created_by_user_id`, `scheduling.appointments.previous_appointment_id`, `finance.payments.reverses_payment_id`, `finance.payment_allocations.reverses_allocation_id` target their own primary key. (h) Polymorphic columns without FK are exactly the four listed in §2.

**Problems found and corrected in this pass:** (1) `pricing_discount_entries` had a composite `(case_work_item_id, visit_id) → case_work_items`, invalid because `case_work_items` has no `visit_id` and no such unique key; replaced by two direct FKs with an XOR CHECK, no `visit_id` column (the Visit is derived, so no duplicated Visit truth). (2) `assistant_overtime_entries` referenced `attendance_records (id, assistant_id)` without that unique key; it now targets the declared `UNIQUE (id, assistant_id, attendance_date)`. (3) `visit_corrections` named an "FK pair (visit_id, doctor_id) → visits" with no unique `(id, doctor_id)` and mismatched column names; it is now a real composite FK. (4) `feedback_entries` composite had no unique `visits (id, patient_id, doctor_id)` and could not link a request; it now links through `feedback_requests`. (5) `prescriptions` and `treatment_records` composites lacked their `visits` unique keys; declared. (6) `installment_payments (ortho_case_id, charge_id) → ortho_cases` lacked `UNIQUE (treatment_case_id, charge_id)`; declared. (7) `revenue_distributions` named an incomplete composite "(payment_allocation_id, …)"; it now has `charge_id` and two explicit composites. (8) `payment_allocations (id, patient_id)` added for the commission item FK. (9) `charge_adjustments.correction_id`, `doctor_earnings`/`distribution_events` "FKs as named" and `staff.doctors` / `sales_employees` `user_id` were unspecified; resolved. (10) `case_work_items.treatment_record_id` was nullable, which made three composite FKs silently skip; now NOT NULL and unique.

**FK AUDIT RESULT: ALL FOREIGN KEYS ARE IMPLEMENTABLE IN POSTGRESQL** (as a design review: every composite FK in the table above has a parent key declared on exactly its referenced column set, types agree, no cascade, no cycle needing deferred insertion, and the only columns without an FK are the four polymorphic ones). The migration test in the Final-correction database tests proves it mechanically when the schema is first generated; this document does not claim that any migration has been run.

**First implementation database gate (mandatory, before any feature builds on the schema).** (1) Create an empty PostgreSQL database. (2) Apply all EF Core migrations in order. (3) Verify every FK, UNIQUE and CHECK constraint documented here (§24 register, Final-correction database test 10). (4) Run the database integration tests (guards G1–G10, role grants, cardinalities, ERD sync). Until this gate passes, PostgreSQL implementability is a **design-level check**, not a runtime proof.
